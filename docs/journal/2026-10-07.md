- Claude bổ sung:
  - Cách cân bằng "tính trước" và "làm tới đâu tính tới đó": hỏi **quyết định này có khó đảo ngược không?**
    - Khó đảo ngược -> nghĩ kỹ ngay: chiến lược ID (đổi sequence <-> UUID khi đã có dữ liệu rất đau), dữ liệu phải ghi ngay lúc xảy ra (`createdAt`, vai trò người hủy - bỏ lỡ là mất vĩnh viễn).
    - Dễ thêm sau -> để sau: `cancelledAt`, logic hoàn tiền, value object gộp người hủy. Hôm nay cố ý không làm.
  - Dữ liệu dùng để kiểm quy tắc nghiệp vụ (`now`) do server quyết định, không tin client.
  - Entity so sánh theo ID, value object theo giá trị. Aggregate: bên ngoài chỉ gọi root, root giữ bất biến, tham chiếu aggregate khác bằng ID. HIS hay dùng anemic model (setter + quy tắc ở service) -> 5 service đổi status, sót 1 chỗ là dữ liệu sai.
  - `final` biến quy tắc "không đổi" thành thứ compiler kiểm.
  - Lombok: domain dùng Java thuần + record; cấm `@Data`/`@Setter` trên aggregate và JPA entity (`toString` lặp vô hạn ở quan hệ 2 chiều, chạm lazy collection, `hashCode` đổi sau khi save).
