- Phác thảo (người làm trả lời từng câu, Claude chỉnh và tổng hợp):
  ```
  F2. Khách đặt lịch
  createNew(customerId, providerId, serviceId, start, duration, now)
    - customerId / providerId / serviceId null  -> IllegalArgumentException
    - duration null hoặc <= 0                   -> IllegalArgumentException
    - start không sau now                       -> IllegalArgumentException
    -> id tự sinh, timeRange = [start, start+duration), status = PENDING_PAYMENT, createdAt = now
    Ngoài Booking: serviceId tồn tại/đang hoạt động (application), trùng lịch provider (bước 6)

  F7. Tiền về
  markPaymentReceived(now)
    - status != PENDING_PAYMENT               -> IllegalStateException
    - now >= createdAt + 15 phút (hết hạn)    -> IllegalStateException
    -> status = CONFIRMED

  F8. Hết hạn giữ slot (job gọi)
  cancelBySystem(now)   (tên tạm, xem lại ở F9)
    - status != PENDING_PAYMENT               -> IllegalStateException
    - chưa quá createdAt + 15 phút            -> IllegalStateException
    -> status = CANCELLED, người hủy = hệ thống
  ```
- Quyết định trong phác thảo:
  - Chọn **A** (truyền `duration`, Booking tự tính end) thay vì B (truyền `TimeRange` tính sẵn): công thức F2 nằm 1 chỗ. Không giải quyết: Booking không biết `duration` có đúng của `serviceId` không (chấp nhận ở Phase 1).
  - Không giữ `duration` làm field (suy ra từ `timeRange`); `start`/`end` gộp thành `TimeRange`.
  - Truyền `now` làm tham số để test tự quyết "bây giờ"; `now` lúc tạo thành `createdAt` (F8 cần). Hằng số 15 phút đặt trong Booking.
  - `markPaymentReceived` chặn tiền về sau hạn 15 phút dù job chưa chạy -> tiền phải hoàn (luồng hoàn này vốn đã cần).
  - `cancelBySystem` tự kiểm tra hết hạn, không tin query của job.
- Thảo luận ngoài lề:
  - **Validate FE vs BE:** BE luôn tự validate; FE chỉ vì UX. Kênh API không có FE. Trong BE: controller/DTO kiểm hình thức, domain kiểm quy tắc nghiệp vụ.
  - **Application vs domain:** application điều phối (tra DB, gọi domain, lưu); domain giữ quy tắc trên dữ liệu được đưa vào. Booking không giữ repository.
  - **Transaction Script (HIS) vs Domain Model:** cả 2 hợp lệ (Fowler 2002, Evans 2003). Công ty lớn: domain model cho core domain, CRUD cho phần phụ trợ; phỏng vấn senior hỏi "vì sao chỗ này dùng, chỗ kia không". Người làm: "với mục tiêu học để nâng trình thì như này là đúng cái tôi cần".
